# 提取与 PDF 处理

本文档描述当前提取流水线，重点放在 PDF 路径，因为它是当前代码里判断最多、复杂度最高的部分。

## 主提取器

当前主提取器由 `src/dite/io/route.py` 中的 `extract_document()` 负责选择。

当前提取器类别包括：

- Docling，用于现代文档格式
- MarkItDown，用于较旧的 Office 风格格式
- 直接文本读取器，用于纯文本和 Markdown
- VLM 提取器，用于图片文件

如果没有匹配到可用提取器，当前提取结果会返回失败的 `ExtractionResult`，内容字符串为空。

## 主提取与最终提取不是一回事

当前提取逻辑实际上分成两段：

1. 主提取
2. 最终内容决策

主提取负责：

- 调用一个提取器
- 不做 PDF 回退判断
- 产出相对稳定、可长期缓存的主内容

最终内容决策负责：

- 评估 PDF 主提取质量
- 读取已有 VLM 回退缓存
- 视情况调用 PDF 的 VLM 采样路径
- 在主内容和 VLM 内容之间选择最终结果

这个切分是当前架构的核心，不是实现细节。

## PDF 决策模型

当前 PDF 路径由这些函数共同决定：

- `src/dite/io/pdf/policy.py` 中的 `build_pdf_decision()`
- `src/dite/io/pdf/final.py` 中的 `resolve_pdf_vlm_fallback()`
- `src/dite/io/pdf/final.py` 中的 `select_pdf_final_content()`

当前决策流程是：

1. 分类主提取得到的 PDF 结果。
2. 决定是否需要 VLM 回退。
3. 决定回退来源是 `cache`、`api` 还是 `none`。
4. 如果可能，取得 VLM 内容。
5. 比较主内容和 VLM 内容质量。
6. 选出最终内容，并决定这份 VLM 内容是否应该写回缓存。

## 什么情况下才会考虑 PDF 的 VLM 回退

当前只有在下面这些条件同时成立时，才会考虑 PDF 的 VLM 回退：

- 文件是 PDF
- VLM 回退开关是开启的
- 主提取器是 `docling`
- PDF 质量画像判断它确实需要回退

这意味着 PDF 回退不是所有文档的通用第二轮处理。

## Docling 的 PDF 页数上限

`processing.docling_pdf_max_pages`（默认 50，设为 `null` 表示不限）让 Docling 只转换 PDF 的前 N 页（通过 `page_range`，不会因为页数多而拒绝文件）。原因：

- 进入后续流程的只是一段摘录（`text_truncate_limit`，默认 4000 字符），转换整本书的绝大部分工作都被丢掉。
- 上百页的书在 CPU 上常常撞上 `docling_pdf_timeout_sec`，然后整份文档转去走 VLM 采样。

50 页以内的文档完全不受影响。更长的文档，摘录的首/中/尾取自前 N 页，而不是整本书（书末通常是索引和参考文献）。

内容缓存只按文件哈希索引，不记录提取设置：已经缓存过的文件会继续使用当时的提取结果。改了这个值想让旧文件也生效，需要先 `dite cache clear`。DOCX/PPTX 等非分页格式不受影响。

## PDF 的 VLM 采样上限

当前 PDF 的 VLM 采样深度是固定的：

- 只采样前 10 页

这是当前实现里的架构常量，不是用户可配置项。

别把它和下面这个配置混淆：

- `processing.vlm_pages_per_document`

这个配置只控制单个 PDF 内部的页级并发量，不控制总采样页数。

## PDF 质量启发式

当前代码会用有效内容长度和 PDF 噪声特征来评估主提取质量。具体评分逻辑在 `src/dite/io/pdf/policy.py` 中。

从行为上看，它意味着：

- 主提取内容过弱或噪声过多时，可能触发回退判断。
- 只要有 VLM 输出，并不代表它一定会被采用。
- 最终内容是主内容和 VLM 内容比较之后的结果。

## 已缓存的 VLM 内容如何处理

如果某个 PDF 已经存在 VLM 缓存：

- 回退来源会被判定为 `cache`
- 不需要再调用 VLM API
- 但即便缓存存在，如果主内容更好，缓存内容仍然可能被放弃

## VLM API 回退路径

如果没有 VLM 缓存，且允许调用 API：

- PDF 页面会先被渲染出来
- 采样页会走 VLM 提取路径
- 页级输出会合并成一段回退文本

如果 VLM API 路径失败：

- 流水线仍然会保留主内容
- 文件级报告里仍然会保留这次回退尝试和页调用计数

## 缓存写入意图

当前最终内容选择阶段会返回一个显式的缓存写入意图。

它的作用是让外围流水线能够分清几种情况：

- VLM 内容来自 API，而且被选为最终内容：应该写缓存
- VLM 内容来自缓存：不需要再写一次
- VLM 内容存在，但没被选中：不写缓存
- 根本没有 VLM 内容：无事可写

这比把缓存判断散落在流水线各处更干净。

## 重复文件处理

当前流水线会在正式提取前先计算文件哈希。

当前行为：

- 每个唯一哈希只选第一个文件作为规范样本进入提取流程
- 其他重复文件复用规范样本的内容和文件级报告
- 重复文件计数会进入提取摘要

这样做能显著减少提取和 embedding 的开销，同时不改变最终报告里的文件成员关系。

## 提取并发控制

当前与提取相关的并发控制参数包括：

- `processing.extract_workers`
- `processing.docling_pdf_workers`
- `processing.vlm_api_workers`
- `processing.vlm_pages_per_document`

当前行为含义：

- 规范样本文件可以并行提取
- Docling 的 PDF 子进程会额外受一个信号量控制
- VLM 请求有全局并发上限
- 单个 PDF 内部的页级 VLM 请求也有局部上限

## 单文件出错与中断

- 某个文件在提取时抛出异常（扫描后被删除、没有读权限、解析器出错、Docling 子进程被 OOM 杀掉等），只把这个文件记为提取失败：打印一条警告，报告里带提取失败标记，其余文件照常处理。
- 读写提取缓存出错（缓存数据库被锁、磁盘已满、只读或损坏，或写缓存时文件已被删除）不算提取失败：打印一条警告，出错的那次读写按未命中处理，提取出的内容照常保留。这个文件的其他缓存查询照常进行（读 Docling 结果出错时仍会查 VLM 缓存，免得重复付费请求 VLM），但本次不再写入缓存。
- 提取阶段按 Ctrl+C 会尽快停下：不再开始新的文件，终止正在运行的 Docling 子进程，也不再发出新的 VLM 请求（正在处理的 PDF 里还在排队的页面也不再发出）；已经发出的 VLM 请求和非 PDF 转换会等它们结束，但结果不再使用。命令随后提示已中断，并以状态码 `130` 退出。

## `pdf-check` 的真实语义

`pdf-check` 当前并不回答“这份 PDF 是否被完整理解”。

它回答的是更窄的问题：

- 最终提取结果是否已经足够可用，达到了配置中的阈值

所以它可能出现两种情况：

- 某个 PDF 明明提取出了一些文本，但仍然被判定失败，因为内容质量不够。
- 某个 PDF 只依赖采样页 VLM 输出，也可能被判定通过，因为最终结果已经跨过可用阈值。
